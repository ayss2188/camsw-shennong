---

关于"手机系统更新到底砍不砍相机画质"，一直是有争议的话题。有人升级后觉得成像变"锐利但发干、塑料感"，有人觉得是"优化"。影溯做的是：把 OS1 出厂那套相机数据，逐项搬回现在的系统上，让想找回 OS1 成像的机友能一键切换、随时对比，觉得不对就一键还原。

一、详细介绍

1. 核心技术：bind mount，为什么不"直接替换系统文件"？

传统改相机的做法，是直接替换 `/odm` 下的系统文件。这种做法有两个致命问题：要动只读分区（风险大、不可逆），而且一旦改坏只能重刷固件。

影溯换了一条更安全的路线——bind mount（绑定挂载）：

- 原理：把模块目录里的 OS1 出厂相机数据，临时"盖"到 `/odm` 对应的文件路径上。相机服务读 `/odm` 时，实际读到的是 OS1 的数据，但物理分区一个字节都没动。
- 内存态：挂载只存在于内存里，卸载模块或重启手机，挂载自动消失，系统 100% 还原原样，零残留、不可逆风险为零。
- 免重启切换：挂载/卸载是即时的，配合守护进程重启相机服务，改完点「应用」就生效，不用每次切换都重启手机。

对比效果：传统替换 = 动分区 + 不可逆 + 每次要重启；影溯 = 不动分区 + 可逆 + 免重启。这也是为什么敢把 212 项开关全部开放给用户随便试的原因——试错成本几乎为零，改崩了重启就回来。

2. 逐项 sha256 指纹校验：状态不是"猜"的

相机文件会随系统更新、相机服务占用、用户操作而变化，光靠"我记得我切过"是不可靠的。所以影溯给每一项都做了指纹校验：

- 记录两个基准哈希：OS1 出厂哈希（写死在脚本数据段）+ 系统原生基线（初始化时对当前系统实测记录）。
- 切换后实时计算 `/odm` 当前文件哈希，和两个基准比对，判定每项是「OS1 / 系统原生 / 异常」三种状态。

效果：WebUI 上每一项的当前状态都是实测出来的。哪项没挂上、哪项文件被系统改动过、哪项异常，一眼可见，不会出现"界面显示切了、实际没生效"的假象。

3. 守护进程架构：为什么 WebUI 直接挂载相机"看不到"？

这里有个很多人踩过的坑：WebUI 自己跑在私有挂载命名空间里，它直接做的挂载只有它自己看得见，相机服务（跑在全局命名空间）是看不到的——这会导致"挂载成功但相机没变化"。

影溯专门内置了一个守护进程（daemon.sh）：WebUI 只负责发指令，真正的挂载由守护进程在全局命名空间里执行，相机才能看到。WebUI 和守护进程之间通过文件通信，省电设计（空闲时每几秒才醒一次）。

这也是为什么首次刷入必须重启一次——重启后守护进程才能拉起，之后才能正常切换。

4. 212 项独立开关，为什么拆得这么细？

相机成像不是"一个开关"能决定的，它由算法核、模型、调校参数、GPU 计算内核、着色器、ISP 校准数据等几十上百个文件共同决定。如果只换一部分、或者整套粗暴替换，很容易出现"风格混搭"的割裂感。

所以影溯把相机影像资产拆成 212 个独立开关，按四大类组织，每一项都能单独切换，也能整链/整套方案切换：

🧑 人像与虚化（31 项）
- 成片虚化链（6 项，整链）：虚化引擎 + 多帧虚化引擎 + 虚化 CL 计算核 + 多帧 CL 内核 + 深度 CL 内核 + DSP 虚化核。管拍完后的背景虚化强弱、焦外光斑形状。
- 人像深度链（5 项，整链）：深度融合宿主库 + 三个插件（portraitsll 超分 / tfsll 超分 / capdepth 深度生成）+ DSP 深度核。人像先算深度图、再做虚化，全靠这条链调度。
- 人像修复（8 项）：前/后置、拍照/live、开虚化等场景的二次精修参数，独立可调。
- 虚化算法库（9 项，整链）：人像视频虚化、单摄虚化、单摄实时虚化、预览虚化、深度计算和补洞等大型算法库，加单摄虚化配置。
- 虚化插件（3 项，整链）：前置虚化插件、单摄虚化节点、实时虚化节点，负责把虚化算法接入拍摄流程。

为什么这些要"整链"？ 因为链上的文件是宿主库 + 插件互相调用的关系，只换宿主库不换插件（或反过来）会导致 ABI 不匹配、相机直接崩。所以这类分组做了整链约束：要么全开、要么全关，杜绝"换一半崩了"的情况。

🧩 成像算法（155 项）
- AI HDR（1 项）：RAW HDR 的 AI 模型，管逆光、强对比下的曝光合成。
- GPU 内核（5 项）：GPU 上的计算内核，负责降噪、锐化、色调映射等底层并行计算。
- GPU 着色器（95 项）：美颜磨皮、面部精修、妆容贴图、基础图像处理的全套渲染程序，体量最大的一组。
- AI 超分 AIUR（4 项，整链）：AI 超分辨率相关的插件、算法库、模型和参数。
- 弱光增强 ELLC（3 项，整链）：弱光场景相关的插件、算法库和模型。
- 夜景增强 SNSC（4 项，整链）：夜景场景相关的插件、算法库、模型和参数。
- HDR 与夜景算法库（6 项，整链）：RAW HDR 合成、超级夜景融合、多帧超分、AI RAW HDR、HDR 场景检测等大型算法库，加多帧超分配置。
- HDR 插件（3 项，整链）：arcsoft RAW HDR、小米 AI RAW HDR、HDR 三个插件，和上一项配套。
- 畸变校正算法库（2 项，整链）：AI 畸变校正算法库及其分割模型。
- CFR 算法库（5 项，整链）：CFR 与图像分割相关的三个算法库，加分割模型和长焦 2 倍参数。
- 基础算法库（6 项）：AI 神经网络基础库、多摄变焦融合、坐标转换、图像形变、慢动作处理等小型算法库，彼此独立。
- 美颜特效数据（21 项）：亮眼、面部立体、面部精修、后置磨皮等美颜特效所用的网格与参数文件，彼此独立。

🔌 插件与节点（20 项）
- 对焦与畸变（3 项，整链）：智能对焦节点、畸变校正节点、畸变校正插件。
- 视频处理（3 项，整链）：后置视频节点、镜头平滑过渡节点、透明度混合节点。
- 辅助插件（14 项）：图像增强（去紫边、AI 去模糊、超分、超级月亮、重马赛克）、拍摄辅助（锚点、定点拍摄、模拟、人脸对齐）、视频相关（夜景视频、视频虚化）、基础工具（内存拷贝、软件翻转），彼此独立，可单项开关。

📐 底层调校（6 项）
- ISP 调校：主摄 / 超广角 / 长焦 / 前置等各模组的曝光、白平衡、锐度校准数据，出厂时就写死在系统里。

说明：以上各分组按文件用途归类。不同场景、不同系统版本和硬件批次下，成像变化各有差异，请以实际拍摄效果为准。

5. 两份 OS1 数据：尽量还原出厂，又保证功能完整

模块内置了两份 OS1 相机数据，目标是尽量还原出厂版本的成像：

- 主数据（191 项）：GPU 内核、GPU 着色器、ISP 调校、美颜特效，以及 2.0 新增的各类算法库、插件和节点，直接用出厂版本（1.0.6.0）的原始数据，把出厂成像"原样搬回来"。
- 补充数据（21 项）：系统更新到 1.0.41.0 后新增了一批相机特性，对应出厂 1.0.6.0 里根本不存在的文件（人像深度链、成片虚化链、AI HDR 等）。这些文件出厂时就没有，自然也无法"还原到出厂"，所以这部分使用 1.0.41.0 版数据，保证功能完整、不因强行还原而缺失或异常。

2.0 新增的算法库、插件和节点，收录前都对照当前系统做过接口核对：接口缺失、或被系统里其他文件依赖的库没有收录，保持系统原版，避免因为强行替换让新功能失效。

一句话：能还原到出厂的就还原，出厂没有的新特性就保持新版，两份搭配，在"贴近出厂成像"和"功能完整不崩"之间取平衡。数据全部内置。

二、WebUI 功能详解（不是"开关列表"那么简单）

🎛 预设方案（快捷切换）
「系统原生 / 全部 OS1」两个方案按钮一键整套切换（全部 OS1 会一次切换全部 21 个分组、212 项）；手动调的组合可以「直接应用」或「存为预设」，支持自定义命名、排序、一键载入。想存"夜景偏好""人像偏好"多套风格随时切，很省事。

🟡🔵 暂存 / 生效双态指示
这是本模块的一个细节设计：点一下变黄（已选、待应用），应用成功变蓝（当前正在生效），点「取消」即还原。顶部还有颜色图例。为什么做这个？ 因为切换不是即时的，中间有个"暂存→应用"的确认过程，黄蓝双态能让用户任何时候都清楚"我选了什么"和"当前跑的是什么"，避免误操作。

🕘 历史记录 / 🗒 运行日志（双轨记录）
- 历史记录：用人话记下你改了什么（如"成片虚化 切到 OS1 ×6"），带图标分类型，一眼看懂操作轨迹。
- 运行日志：保留原始技术日志，出问题排查用。两者分开——一个给人看、一个给排查看。

⬆️⬇️ 导入导出
自带文件浏览器，配置一键备份/恢复，换机、重装、分享配置都方便。

♻️ OTA 自愈
系统更新后，相机基线变了、旧的挂载可能失效。点一下自动恢复并重新校准基线，避免"升级后模块失灵"。

↩️ 崩溃自动回退
守护进程实时盯着相机服务，一旦发现相机反复崩溃，自动恢复系统原生并清空自动应用，不会让相机一直坏着。

🌓 主题
浅色 / 深色 / 跟随系统三档。

🔄 管理器内检查更新
在 Magisk / KernelSU / APatch 的模块页就能检查更新、查看更新日志。检查更新需要能访问 GitHub，网络不通时请到发布页手动下载。

⚡ 开机自动应用
可开可关；关则每次重启回到系统原生（最安全），开则重启后自动重新应用上次的选择。

五、详细刷入与使用教程

KernelSU / SukiSU / APatch 纯净版
1. 管理器 → 模块 → 从存储安装 → 选 `camsw_shennong_v2.0.zip`。
2. 刷入完成后重启一次手机。
3. 回管理器，模块卡片点「WebUI」。
4. 工具箱 →「初始化」→ 部署数据并记录系统基线（数据量较大，需要几分钟，请耐心等待）。
5. 切换页逐项或按方案选「系统 / OS1」→ 底部「应用」。
6. 建议先只开一两项（比如「成片虚化」）试拍，确认没问题再逐步增加；整链分组只能整组开关。项目较多时一次应用可能需要几分钟，期间请不要打开相机。

六、关键设置：解决"部分生效 / 没完全变"问题

如果切换后发现相机"有的变了、有的没变"（比如某个分组状态显示不一致）：

- 原因：通常是切换时对应文件被相机服务占用，导致恢复/挂载没成功；或者守护进程还没同步过来。
- 解决：
  1. 工具箱 →「状态修复」，让实际状态与保存的选择一致；
  2. 再点「一键修复」复位 DSP 与相机服务（约 15 秒）；
  3. 仍不行就重启一次手机，重启后挂载恢复原样、重新应用即可。

七、关键说明与已知局限

- 非全量移植：无法 100% 还原 OS1 成像，只能一定程度回退。不同版本间的成像差异，更偏向「成像风格的取舍」，以自己实拍观感为准。
- 换系统需重新校准：系统升级后，请重新「初始化」并逐项测试，尤其是人像深度/成片虚化两条有库依赖的链，风险比纯数据项高。
- 效果因人而异：各分组对成像的影响因场景、系统版本和硬件批次而异，本模块不对具体效果作任何保证，请以实际拍摄效果为准；觉得不合适，随时在「系统原生」下应用，即可恢复原样。
- 兜底机制：崩溃自动回退、一键修复、重启还原，三重保险，改崩了也不慌。
